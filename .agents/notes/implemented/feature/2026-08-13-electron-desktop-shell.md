# Agent Note: Electron desktop shell for the web UI

Status: implemented

English | [中文](2026-08-13-electron-desktop-shell.zh.md)

## Problem

DeepSeek Harness is a web application embedded in the `dsh` CLI: using the UI requires manually starting `dsh web` and keeping a browser tab on `http://127.0.0.1:3080`. There is no native desktop entry point that starts the server, presents the UI, and stops the server with itself. The repo's app tier (`apps/*`) has a CLI and a web frontend but no desktop assembly.

## Decision

Add `apps/desktop`, an Electron shell that hosts the existing web UI as a native desktop application. The Electron main process (`src/main.mjs`) walks from the package up to the `@deepseek-ai/dsh-root` marker, spawns `dsh web` as a child from that root, polls the default URL until it returns HTTP 2xx, and opens a hidden-then-shown `BrowserWindow` on that URL. The server is torn down with the app: `taskkill /T` on Windows, a process-group signal on POSIX (the child is detached into its own group). The window keeps `nodeIntegration` off, `contextIsolation` on, and `sandbox` on, and delegates external links to the system browser.

A `--smoke` flag is the deterministic check: it starts the server, loads the window once without surfacing it, captures `smoke/smoke.png`, prints the page title, tears the server down, and exits non-zero on any failure. `DSH_DESKTOP_PORT` overrides the default port. `electron` is listed in the workspace `allowBuilds` because pnpm otherwise blocks its binary-download postinstall. `resources/icon.png` is generated by a zero-dependency Node script.

## Alternatives considered

**A standalone desktop directory outside the workspace.** Rejected because the shell is a first-class application and `apps/*` is the app tier; a non-workspace entry would not resolve Electron through pnpm, would not be discoverable alongside `apps/cli` and `apps/web`, and would sit outside the repo's conventions.

**Reusing an already-running `dsh web` instance on the default port.** Rejected because the config and working directory of a foreign server are not ours, and silently attaching to it makes the app's behavior depend on an unknown external process.

**Exposing the harness to Node from the renderer.** Rejected because the web UI needs no Node access to work; the strict `contextIsolation`/`sandbox` defaults keep a remote-capable surface isolated from the process tree the shell owns.

## Consequences

The harness now runs as a desktop application: the shell owns the server lifecycle, so it starts, serves, and is torn down with the app window. Because the shell spawns its own server, launching it while another `dsh web` holds the default port fails loudly rather than silently attaching. The shell is currently source-run only; a packaged distributable that bundles the server and a runtime is deliberately out of scope and noted as future work in `apps/desktop/README.md`. The `main.mjs` entry is ignored by oxlint and outside the repo's TypeScript build programs (it is plain Electron-main ESM), so it adds no typecheck or lint surface to existing packages.
